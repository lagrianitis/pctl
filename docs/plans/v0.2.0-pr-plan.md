Four constraints fixed this shape:

- **`src/pctl/azure/graph.py` accumulates.** Seven of the nine PRs touch it, each adding
  the transport methods its own service needs. Reordering them means resolving conflicts in
  one file repeatedly, which is the whole reason the stack is linear.
- **`src/test/smoke/test_cli_surface.py` enumerates the command tree.** `COMMAND_PATHS`
  gains an entry per command, so it is modified by six of the nine PRs. A PR that adds a
  command must carry its own line in that list or the surface test fails on that branch.
- **The named-flag refactor has to come after every service it rewrites.** `7993a20`
  touches 34 files including the tests of all six preceding PRs. Landing it earlier would
  mean writing each later service twice.
- **`azure/common.py` is created in PR 3 but used by PR 2's code.** `e5a3064` lifted the
  directory lookups out of `service_principals/common.py` once `users` needed them too, so
  PR 3 refactors what PR 2 introduced. That is the correct order — the abstraction arrived
  with its second caller, not before it.

**Nine PRs is more than anyone wants to review.** The v0.1.0 plan proposed five and
delivered three. Reasonable collapses, if you would rather have four:

- 1 + 2 into one `sp` PR (26 files): the read commands and the owner writes.
- 3 + 4 into one directory PR: `users` and `apps` are both thin services over shared

- 5 + 6 into one `eam` PR (27 files, +3193): reads and writes of the same service.
- 8 stays alone. It contains the only destructive command in the CLI and deserves its own
  review.

What should **not** be collapsed is PR 7. It is the only breaking change, it touches both
provider cases, and it is what every downstream caller has to react to.

## How the splitting works

The history is linear and each PR is a contiguous range, so every branch is one command and
nothing is rewritten:

```bash
git branch feature/azure-sp-reads         d25bf64
git branch feature/azure-sp-owners        457d812
git branch feature/azure-users            893daa3
git branch feature/azure-apps             eb8f5b2
git branch feature/azure-eam-reads        da6fbf4
git branch feature/azure-eam-writes       64bcac6
git branch feature/named-flags            <see below>
git branch feature/azure-provision-delete ca40415
```

No cherry-picking, no staging, no stashing. Verify each with
`git log --oneline <parent>..<branch>` before opening anything.

PRs 1 through 6 point at commits that are **already on the remote**, so pushing those
branches transfers no new objects and cannot change what anyone else sees.

## Blocker: the formatter conflict

`4aefafb` sits between `c06e242` and the rest of the stack, so PR 7 inherits it. It has to
go one way or the other first. It is **not pushed**, so rewriting it is legal — the rule
against rewriting published history does not apply.

**Option A — drop it and keep ruff (recommended).** `ruff format` is already
Black-compatible, so adopting Black buys nothing and costs a dependency plus a rewrite of
the rule in `.kiro/steering/code-style.md` that currently forbids it.

```bash
git switch feature/azure-service-principals
git rebase --onto c06e242 4aefafb          # drops the churn commit, keeps the three above it
uv run --no-sync ruff format src/          # normalise anything the drop left at 88
uv run --no-sync ruff format --check src/  # expect: all files already formatted
git commit -am "style: restore ruff formatting"   # only if the previous step changed files
git branch feature/named-flags HEAD~2      # the flag commit, now without the churn below it
```

This **permanently discards** the Black run. It was never pushed and git has no other copy.

**Option B — adopt Black.** Declare it rather than leaving it undeclared:

```bash
uv add --group dev black
# then in pyproject.toml:
#   [tool.black]
#   line-length = 100
#   target-version = ["py314"]
uv run black src/                          # through uv, so it runs on 3.14
```

The system Black is 24.1.1 on Python 3.12 and **cannot parse this codebase** — it dies on
`graph.py`'s PEP 758 bracket-less `except TypeError, ValueError:`. That is why the churn
commit formatted some modules and skipped others. Option B also means swapping
`ruff format` for `black` in `.github/workflows/ci.yml`, rewriting `code-style.md`, and
carrying `uv.lock` churn in whichever PR takes it.

Whichever you pick, it lands in PR 7 and nothing above PR 7 is affected.

**The first commands in `pctl` that write anything.** Two details are worth a reviewer's
attention:

- `remove_owner` issues `DELETE /servicePrincipals/{id}/owners/{ownerId}/$ref`. Without the

The reason this service exists separately from `sp`: **an application has two GUIDs and

**Entitlement management has a narrower OData surface than the rest of Graph**, and that
constraint shapes the whole service. `$select`, `$filter` and `$expand` work; `$search`
and `$count` do not. So:

- `_governance_params` is deliberately separate from `_list_params`, which adds

- Match modes are `exact | prefix | contains`, not `search`. `contains` filters locally and

- `get-package` and `get-catalog` return **every** pattern match rather than refusing an
  ambiguous one, because "show me the AWS packages" is a question with several answers.
  One match renders as an object and several as an array, the shape `groups get` uses.

### Review notes

**Assignments are not written directly.** Both commands create an
`accessPackageAssignmentRequest` that Graph then processes, so they are asynchronous and
exit 0 without `--wait` does not mean the access exists. That matters more for removal than
for addition: revoking access in an incident and getting exit 0 does not mean the access is
gone.

Two API details encoded once so they are not rediscovered:

- The v1.0 body is `{"requestType": "adminAdd" | "adminRemove", "assignment": {...}}`.
  Beta used `AdminAdd` and `accessPackageAssignment`, so a body copied from a beta example
  is rejected here.

### Review notes

Keep this PR separate. It contains **the only destructive command in the CLI**, and the two
commands in it are the ones most likely to need a second opinion.

`sp provision` — **a 200 from Graph does not mean a subject was provisioned.** The verdict
is JSON encoded inside the `key` string of a `stringKeyStringValuePair`. Outcomes:
`applied` for Success, `already-in-sync` for a `RedundantExport` skip, `failed` for
everything else including other skip reasons, because an out-of-scope or unassigned subject
comes back as `Skipped` with nothing provisioned. Subjects are sent one request each,
sequentially: Graph rate limits this action to 5 requests per 10 seconds.

`eam delete-package` — three guards, each deliberate. No `--match` and **no substring
fallback**, unlike every other `eam` command, because `Retired` resolving to
`Retired Access` is not a mistake worth risking on a delete. A confirmation prompt after
resolution, so it names what is about to go, declining aborts non-zero. And an assignment
pre-check, because Graph refuses to delete a package with any assignment and a bare 400
does not say what to remove.
