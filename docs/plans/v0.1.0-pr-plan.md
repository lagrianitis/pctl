# v0.1.0 delivery plan

How the current working tree gets from one `Initial commit` to a released `v0.1.0`,
split into five stacked pull requests.

- **Remote:** `origin` → `https://github.com/lagrianitis/pctl.git`
- **Base branch:** `main` (currently `1520c34 Initial commit`)
- **Commit identity:** `Lefteris Agrianitis <lagrianitis@users.noreply.github.com>`,
  set locally. Correct for a public GitHub remote, no corporate address involved.
- **Version in `pyproject.toml`:** `0.1.0`, matching `src/pctl/__init__.py`.

## Working tree inventory

76 untracked files plus one modified file (`.gitignore`). `.kiro/steering/bt.md` is
gitignored and stays local. `IGNORE-helpers/` is gitignored and out of scope.

## Stack order and why

The order is a dependency order, not a preference. Each PR is reviewable on its own and
leaves CI green, given the one caveat noted under PR 1.

| # | Branch | Depends on | Adds |
| --- | --- | --- | --- |
| 1 | `chore/repo-foundation` | `main` | packaging, CI, templates, steering |
| 2 | `feature/cli-core` | 1 | root group, shared runtime, shared unit tests |
| 3 | `feature/azure-graph` | 2 | `pctl azure` case and its tests |
| 4 | `feature/aws-dynamodb` | 3 | `pctl aws ddb` case and its tests |
| 5 | `feature/e2e-smoke-and-docs` | 4 | cross-case smoke tier, e2e scripts, README |

Three constraints drove this shape:

- `pyproject.toml` and `uv.lock` must land first. Both CI jobs start with
  `uv sync --frozen`, so nothing can be linted or tested before they exist.
- `src/pctl/cli.py` names both cases in `LAZY_COMMANDS`. Resolution is lazy, so
  `pctl --help` renders before the case packages exist. Nothing needs editing as the
  stack lands.
- `src/test/smoke/test_cli_surface.py` walks the whole command tree, including
  `azure groups get` and `aws ddb scan`. It has to be last, which is why it sits in
  PR 5 rather than with the core.

**Caveat on PR 1.** Its tree has no Python, so the `test` job runs `uv run pytest` with
nothing to collect and exits 5. Either land PR 1 and PR 2 back to back and accept one
red `test` job on the scaffolding PR, or squash the two. Everything from PR 2 onward is
green.

## How the staging works

Everything is currently untracked in one working tree, which makes this easier than it
looks. **Untracked files survive a branch switch**, so there is no stashing and no
moving files about. Each branch stages its own subset, commits, and leaves the rest sitting
in the working tree for the next branch to pick up.

```bash
git switch -c chore/repo-foundation          # branch off main
# stage and commit only PR 1's paths, per the commands below
git switch -c feature/cli-core               # branches off chore/repo-foundation
# PR 2's files are still untracked and waiting
```

Conventions used in the command blocks below:

- **Paths are explicit.** No `git add .` and no `git add -A`: with the whole project
  untracked, either one would sweep every remaining file into the first commit.
- `git commit -m "subject" -m "body"` — repeated `-m` flags become separate paragraphs.
  Where a body runs to several paragraphs, use the `git commit -F -` heredoc form shown
  in PR 1.
- **Check before you commit** with `git status --porcelain -uall` and
  `git diff --cached --stat`. The staged set should match the listed paths exactly.
  `git add --dry-run <paths>` is the cheapest way to see what a command would take.
- **`git ls-files --others` will not list `.kiro/steering/`,** even though `git add` and
  `git status` both handle it. The global `core.excludesFile` excludes `.kiro`, and the
  repo's `!.kiro/` negation is honoured by one and not the other. `git add
  .kiro/steering/` stages all 13 files correctly; verify with `git status`, not
  `ls-files`.
- **Commits inside a PR are logical chunks, not individually green.** They are ordered so
  each one is importable (dependencies first), but CI validates the branch head, which is
  what the merge sees.

One guard worth running once, before the first commit, since the remote is public:

```bash
git remote -v                    # expect github.com, not the internal server
git config user.email            # expect the noreply address, not a corporate domain
```

git commit -m "feat(errors): map failures to exit codes" \

code contract stays in one place: 2 usage or config, 3 auth, 4 not found,

# 2. config: imports errors

git commit -F - <<'MSG'
feat(config): add app context and credential resolution

AppContext rides on click.Context.obj, so leaf commands read app.output,
app.quiet, app.verbose and app.columns instead of threading globals through
every signature. Provider config is derived on demand via app.azure() and
app.aws().

Credentials resolve in a fixed order: environment variables, then AWS Secrets
Manager by id, then the provider's own chain (the boto3 chain for AWS,
DefaultAzureCredential for Azure). No credential is ever read from a flag, and
credential fields are kept out of repr.
MSG

# 3. output: imports config
git add src/pctl/output.py
git commit -m "feat(output): add streaming renderer" \
  -m "Renderer is a context manager covering table, json, ndjson and csv. The
last three stream through orjson straight to stdout, so memory stays flat
regardless of result size; table buffers because it has to measure columns." \
  -m "Data goes to stdout and summaries to stderr via summarise(), which is what
keeps pipes clean."

# 4. credential storage, both leaf modules
git add src/pctl/tokencache.py src/pctl/secrets.py
git commit -F - <<'MSG'
feat(auth): add token cache and secret lookup

Client-credentials tokens are cached under ${XDG_CACHE_HOME:-~/.cache}/pctl/
tokens with 0600 files inside a 0700 directory, which saves a 150-400ms round
trip to Entra ID on every repeat call. Corrupt and expired entries are treated
as a miss rather than an error, so a bad cache degrades to a slow path instead
of a failure.

secrets.py resolves Azure credentials from AWS Secrets Manager by id, so the
secret value never has to reach argv, shell history or a config file.
MSG

# 5. the CLI surface, last because it depends on all of the above
git add src/pctl/lazy.py src/pctl/options.py src/pctl/cli.py src/pctl/__main__.py
git commit -F - <<'MSG'
feat(cli): add root group and lazy dispatch

cli.py imports only click and the stdlib. PctlGroup resolves subcommands from a
name -> ("module:attr", short_help) table, so --help renders the whole tree
without importing any of it and adding a command is one table entry. The short
help lives in the table for exactly that reason.

Also handles unambiguous prefix matching and aliases (az, graph, ddb), naming
the candidates rather than guessing when a prefix is ambiguous.

options.py holds the shared option groups whose callbacks write into
AppContext: output, columns, azure and aws.
MSG

git commit -F - <<'MSG'
feat(azure): add Graph transport and client wiring

graph.py owns the wire: client-credentials token acquisition, retry with
backoff on throttling and 5xx, and @odata.nextLink pagination. Page N+1 is
requested while page N is still being written, which hides a full round trip
per page on an API that only offers sequential paging.

Payloads are narrowed server-side with $top=999 and $select, cutting both the
number of pages and the bytes per page. OData literals are escaped at the
boundary, and ConsistencyLevel: eventual is sent only for the queries that
require it.

azure/__init__.py holds the `azure` group and the graph_client() wiring every
action in this case shares. httpx is imported inside the function body, never
at module scope, so it stays off the --help path.
MSG

# 2. case-level actions, no service between them and the group
git add src/pctl/azure/token.py src/pctl/azure/raw.py
git commit -m "feat(azure): add token and raw actions" \
  -m "token prints a masked token and its expiry by default; --raw is an explicit
opt-in because it writes a bearer token to stdout. --decode shows JWT claims
without verifying the signature, which is for inspection and not for
authorization decisions. --clear-cache drops cached tokens." \
  -m "raw calls any Graph path with auth, retries and pagination already handled,
so a one-off query does not need a new command."

# 3. the groups service: common.py first, it is what the actions share
git add src/pctl/azure/groups/
git commit -F - <<'MSG'
feat(azure): add groups list, get and members

list follows nextLink across the whole tenant with optional server-side
filtering. get resolves display names concurrently on one keep-alive pool, in
exact, prefix or search mode, and can pull members, owners and counts. members
streams direct or transitive membership.

--from-file reads one display name per line and ignores blanks and # comments,
so a curated list can live in version control.

Shared options and resolution helpers live in common.py rather than
__init__.py: a package namespace also receives its submodules as attributes, so
`groups.list` would shadow the helper. __init__.py re-exports and declares
__all__.
MSG

# 4. tests: unit for the transport, smoke for the surface
git add src/test/unit/azure/ src/test/smoke/conftest.py src/test/smoke/azure/
git commit -m "test(azure): cover Graph transport and CLI surface" \
  -m "Unit tier stubs HTTP with respx rather than mocking httpx objects, covering
OData escaping and the advanced-query headers. Smoke tier checks the azure
surface through CliRunner." \
  -m "smoke/conftest.py strips provider credentials from the environment for every
test in the tier, so a developer's real tenant can never be reached."

git log --oneline main..HEAD
git status --porcelain -uall     # expect only src/pctl/aws, its tests, the e2e scripts, README
