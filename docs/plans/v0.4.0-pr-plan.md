### Review notes

**On `apps`, not `sp`.** Client secrets and certificates are properties of the application
object, so the command sits beside `apps get` and reuses `resolve_application`, selecting
only the fields it needs. Service principals can hold credentials too, but that is a
different object and a different command, so it is left out.

**No new endpoint.** The credentials arrive as `passwordCredentials` and `keyCredentials` on
the application, so the transport gains no method and the command asks for its fields with
`$select`.

**Metadata only.** Graph does not return the value of an existing secret. The command shows
what Graph returns and nothing else, and never prints a certificate's key material. Creating
or rotating a secret is a write with a value shown once, and a different decision.

**The status rule takes the time as a parameter.** `valid`, `expiring` and `expired` are a
function of an end date, a window and a moment. Passing the moment in is what lets the tests
sit exactly on the boundaries instead of drifting with the calendar.

**Dates are UTC, shown as Graph sends them.** The days remaining are whole days from the
moment the command runs, negative or zero once a credential has lapsed.

**Exit 6 for a check that said no.** The issue left the code open. 6 is the next free one,
and it gets its own error class, `CheckFailedError`, so a pipeline can tell "the check ran
and failed" from exit 5, "the provider failed before there was an answer". `--fail-on-expiry`
still lists everything first, so the failure arrives with its detail. An app with no
credentials, or a credential with no end date, passes.

**The flag is `--fail-on-expiry`, the window is `--expiring-within`.** The window is
inclusive at its edge and the deadline is not: a credential ending this instant has lapsed,
one ending exactly a window from now is still expiring.

**The clock is read in one place.** `utcnow()` is a function of its own, which is how the
end-to-end tests pin "now" without freezing anything else.

```markdown
# Summary

Adds `pctl azure apps credentials`, which lists the client secrets and certificates of an
app registration, found by app ID, object ID or display name, with the days each has left
and whether it has lapsed. It can also fail when one is close, so a pipeline can catch an
expiring secret before it breaks an application.

## Changes

- Add `apps credentials`, reusing `resolve_application` so the same name or GUID works as in
  `apps get`, and an ambiguous display name is refused.
- List one row per secret and per certificate, soonest to end first: type, name, key ID,
  start and end date, and the hint for a secret. Rows are built field by field, so a secret
  value or key material in the response is never printed.
- Add the days remaining and a `valid`, `expiring` or `expired` status, with
  `--expiring-within DAYS` for the window.
- Add `--fail-on-expiry`, which lists everything and then exits 6 if any credential has
  expired or is expiring. Exit 6 is new, as `CheckFailedError`.
- Document the command in the README and on the wiki, including exit 6.
- Add the v0.4.0 milestone definition, release notes draft and this plan.
```

## What was and was not verified

Checked, by reading the code and `git`:

- **The lookup is reused unchanged.** `resolve_application` takes a `select` and handles a
  GUID, a display name and an ambiguous name, so the command adds only its field list.
- **The transport needed no new method.** `get_application` and the display-name search both
  accept a `select`.
- **The request shapes in the fakes.** The filters the fake Graph matches on
  (`displayName eq`, `startswith(displayName,...)`, `appId eq`) were read from
  `find_by_display_name`, not assumed.
- **The arithmetic in the tests.** Each expected number of days was worked out by hand from
  the pinned clock, including a leap day between 2027 and 2028.
- **Exit 6 collides with nothing.** The existing codes are 0 to 5, 130 and 141.

Not verified, and this is the important part:

- **No test has run.** About a hundred were added across the three tiers. The e2e fake routes
  are the likeliest to need a fix, because they decide what to return by reading the request.
- **`ruff check` has not been run.**
- **The Graph field names are documented, not confirmed.** `passwordCredentials`,
  `keyCredentials`, `endDateTime`, `startDateTime`, `keyId`, `displayName` and `hint` were
  taken from the Graph documentation. A real call to an app with two secrets was made, but
  its content was not compared with the fakes.
- **The permission is assumed to match `apps get`.** `Application.Read.All` or
  `Directory.Read.All` is expected to read the credentials, and the documentation says so.
- **Whether a certificate's name and hint are always present is unknown.** The rows
  tolerate missing values, and a test covers it.
- **Seven fractional digits in a timestamp** are parsed on the strength of the Python 3.11
  documentation, and a unit test covers them. A real response was not checked for the form.

## Releasing v0.4.0

This PR is the only one in the milestone, so it is the final PR in the sense of
`create-pr.md`. After this PR has merged:

1. Bump `[project].version` to `0.4.0` in `pyproject.toml` and refresh `uv.lock`, so the
   `tag` job's version check passes. `__version__` reads the package metadata, so there is
   nothing else to change.
2. Rewrite `docs/releases/v0.4.0.md` against what shipped, replace the `_pending_` PR entry
   with the real number, and drop the unreleased note.
3. Flip `Status` in `docs/milestones/v0.4.0.md` to ✅ Complete, with the release link.
4. Publish the release on GitHub with the filled notes. The `tag` job verifies the tag
   against `pyproject.toml`, and the `wiki` job publishes the changed pages.
5. Read the `wiki` job's log, then check the Wiki tab: the `Azure-Applications` page shows
   the new command and its links resolve.
6. Close the milestone on GitHub.
