### Review notes

**On `apps`, not `sp`.** Client secrets and certificates are properties of the application
object, so the commands sit beside `apps get`. Service principals can hold credentials too,
but that is a different object and a different command, so it is left out.

**Listing needs no new endpoint.** The credentials arrive as `passwordCredentials` and
`keyCredentials` on the application, so the listing asks for them with `$select`. Only the
two writes add transport methods, `addPassword` and `removePassword`.

**Listing is metadata only.** Graph does not return the value of an existing secret, and the
listing never prints a certificate's key material. Rows are built field by field, so a value
in a response is not printed.

**The status rule takes the time as a parameter.** `valid`, `expiring` and `expired` are a
function of an end date, a window and a moment. Passing the moment in is what lets the tests
sit exactly on the boundaries instead of drifting with the calendar. The force rule for
removal reuses the same window, so the two commands agree on where the line is.

**Exit 6 for a check that said no.** The issue left the code open. 6 is the next free one,
and it gets its own error class, `CheckFailedError`, so a pipeline can tell "the check ran
and failed" from exit 5, "the provider failed before there was an answer".

**The flag is `--fail-on-expiry`, the window is `--expiring-within`.** The window is
inclusive at its edge and the deadline is not: a credential ending this instant has lapsed,
one ending exactly a window from now is still expiring.

**`add-client-secret` is arranged around a value that is shown once.** It refuses to run with
neither `--store-in` nor `--show-secret`. It checks the Secrets Manager secret before the
secret exists (present, live, a JSON object, no clashing key unless `--overwrite`). It
refuses a name the app already uses. If storing fails it removes the new secret again, and
if even that fails the message carries the key ID.

**A create is never repeated after an unknown outcome.** `request` takes `idempotent=False`
for it, which retries only 429. A 500 or a dropped connection could mean the secret exists,
and sending again could leave two with only one held.

**The stored expiry is the one Graph reports.** A tenant policy can shorten a secret, and
the real end date is the one worth keeping.

**`remove-client-secret` takes a key ID and nothing else.** Names are not unique and removal
is permanent. A secret with more than 30 days left, or none, needs `--force`. A certificate
is refused, because Graph asks for proof of possession to remove one.

**`--app-name` and `--app-id`, exactly one.** `--app-id` skips the display name search. It
still makes one request, for the object ID, the display name used in the key names, and the
existing secrets. Object IDs are no longer accepted by these commands. `apps get` and `sp`
keep `--app`, which is a separate decision.

**The clock is read in one place.** `utcnow()` is a function of its own, which is how the
end-to-end tests pin "now" without freezing anything else.

### Description

```markdown
# Summary

Adds `pctl azure apps get-client-secrets`, `add-client-secret` and `remove-client-secret`.
The first lists the client secrets and certificates of an app registration with the days
each has left and whether it has lapsed, and can fail when one is close. The second creates
a client secret and stores its value in an AWS Secrets Manager secret, because Graph shows
it only once. The third removes one, by key ID, and needs `--force` for a secret with more
than 30 days left.

---

## Changes

- Add `apps get-client-secrets` with the days remaining and a `valid`, `expiring` or
  `expired` status, `--expiring-within DAYS` for the window and `--fail-on-expiry`, which
  lists everything and then exits 6. Exit 6 is new, as `CheckFailedError`.
- Add `apps add-client-secret`: `--store-in SECRET_ID` adds `<app>_<name>_client_id`,
  `_client_secret` and `_client_exp_date` to an existing JSON secret and keeps its other keys,
  and `--show-secret` prints the value once. It refuses to create a secret with nowhere to
  put it, vets the destination first, refuses a name already in use, and removes the secret
  again if storing fails.
- Never repeat a create after a server error or a dropped connection. Only 429 is retried.
- Add `apps remove-client-secret --key-id`, with `--force` for a secret that still has more
  than 30 days left or no end date.
- Name the app with `--app-name` or `--app-id` on all three. `--app-id` does no display name
  search.
- Document the commands in the README and on the wiki, with the Secrets Manager key format,
  the IAM actions and exit 6.
- Add the v0.4.0 milestone definition, release notes draft and this plan.
```

## What was and was not verified

Checked, by reading the code and `git`:

- **The lookups are shared.** `resolve_app` in `common.py` takes a `select` and handles an
  appId, a display name and an ambiguous name. `resolve_application`, which `apps get` uses,
  keeps its wording, because the display name path takes the advice text as a parameter.
- **The request shapes in the fakes.** The filters the fake Graph matches on
  (`displayName eq`, `startswith(displayName,...)`, `appId eq`) were read from
  `find_by_display_name` and `find_application_by_app_id`, not assumed.
- **The arithmetic in the tests.** Each expected number of days was worked out by hand from
  the pinned clock, including a leap day between 2027 and 2028.
- **Exit 6 collides with nothing.** The existing codes are 0 to 5, 130 and 141.
- **No new dependency.** `moto[dynamodb]` already covers Secrets Manager, so
  `pyproject.toml` and `uv.lock` are unchanged.
- **No secret value in a message.** The Secrets Manager errors carry the provider's own
  message, never the value, and the report omits `secret` unless `--show-secret` was given.

Not verified, and this is the important part:

- **No full green run and no CI run.** Parts of the suite were run locally and two
  assertions were fixed; the rest is unconfirmed. The e2e fake routes are the likeliest to
  need a fix, because they decide what to return by reading the request.
- **The Graph field names are documented, not confirmed.** `passwordCredentials`,
  `keyCredentials`, `endDateTime`, `startDateTime`, `keyId`, `displayName`, `hint` and, for a
  new secret, `secretText` were taken from the Graph documentation. A real call to an app
  with two secrets was made, but its content was not compared with the fakes.
- **The permissions are assumed.** `Application.Read.All` or `Directory.Read.All` should read
  the credentials, and `Application.ReadWrite.All` or `Directory.ReadWrite.All` should run
  `addPassword` and `removePassword`. The documentation says so; no tenant has.
- **A real Secrets Manager write.** moto accepts what Secrets Manager accepts in the cases
  tested, but a real `PutSecretValue` through the intended IAM policy has not been tried.
- **Whether a certificate's name and hint are always present is unknown.** The rows
  tolerate missing values, and a test covers it.
- **Seven fractional digits in a timestamp** are parsed on the strength of the Python 3.11
  documentation, and a unit test covers them. A real response was not checked for the form.
- **Retrying `removePassword` after a lost response.** The removal is retried like any other
  idempotent request, and a second attempt after an applied first one may report that the key
  is gone. That edge has not been exercised.

## Releasing v0.4.0

This PR is the only one in the milestone, so it is the final PR in the sense of
`create-pr.md`. After this PR has merged:

1. Bump `[project].version` to `0.4.0` in `pyproject.toml` and refresh `uv.lock`, so the
   `tag` job's version check passes. `__version__` reads the package metadata, so there is
   nothing else to change.
2. Rewrite `docs/releases/v0.4.0.md` against what shipped, replace the `_pending_` PR entry
   with the real number, and drop the unreleased note.

4. Publish the release on GitHub with the filled notes. The `tag` job verifies the tag
   against `pyproject.toml`, and the `wiki` job publishes the changed pages.
5. Read the `wiki` job's log, then check the Wiki tab: the `Azure-Applications` page shows
   the three commands and its links resolve.
6. Close the milestone on GitHub.
