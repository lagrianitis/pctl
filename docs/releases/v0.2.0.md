## Overview

`pctl azure` grows from one service to five, and from reading the directory to changing it.
v0.1.0 could list groups; v0.2.0 answers the questions that come up in an access review —
who is assigned to this application, who owns it, what access packages exist and who holds
them — and then lets you act on the answer.

It also removes the last positional argument from the CLI. That is a **breaking change** for
seven commands released in v0.1.0; see [Changed](#changed).

And it ships a user manual: fifteen wiki pages covering every command, the permissions each
one needs, the output formats and exit codes, and the failures people actually hit. They
live in the repository and are published to the GitHub wiki with the release, so the wiki
always describes a version you can install.

## Added

- **`pctl azure sp`** — service principals, which the Entra ID portal calls Enterprise
  Applications. `list` narrowed server-side with `--search`, `--starts-with`, `--filter` or
  `--app-id`; `get` resolving by display name and optionally attaching assignments and the
  app roles an application exposes; `assignments` answering who has access via
  `appRoleAssignedTo`, with `--outbound` for the reverse question. Each assignment gains an
  `appRoleName` resolved from the app's own roles, so `appRoleId` never surfaces as a bare
  GUID, and the all-zero GUID renders as `Default Access`.
- **Scriptable access checks** — `--principal` matches `exact` (default), `prefix` or
  `contains`, all case-insensitive, and exits 4 when nothing matches.
- **`pctl azure sp owners`, `add-owner`, `remove-owner`** — the first commands in `pctl`
  that write anything. An owner is named by email address, display name or object ID,
  distinguished without a flag. Both writes are idempotent: an existing owner or an absent
  one is reported as information on exit 0, so re-running from a pipeline is safe.
  `remove-owner` warns when a removal would leave fewer than two owners, Microsoft's
  recommended minimum, without refusing.
- **`pctl azure sp provision`** — on-demand provisioning, the portal's "Provision on
  demand". Pushes named users or groups through an application's connector immediately
  instead of waiting for the 40-minute cycle. Reports a per-subject outcome of `applied`,
  `already-in-sync` or `failed`, and exits 5 if anything did not provision.
- **`pctl azure users get`** — resolve a person to their directory object from an email
  address, a display name or an object ID. An address is matched against both
  `userPrincipalName` and `mail`, since those routinely differ. An ambiguous display name is
  refused rather than guessed.
- **`pctl azure apps`** — application registrations, the app objects behind service
  principals. `list` and `get`, where `get` accepts a display name, an `appId` or an object
  ID, and `--with-sp` attaches the service principal that instantiates the app in this
  tenant.
- **`pctl azure eam`** — entitlement management. `list-packages`, `get-package`,
  `list-catalogs`, `get-catalog` and `list-assignments`, with `--match exact | prefix |
contains`. The two `get` actions are pattern searches: they return every match rather than
  refusing an ambiguous one, rendering a single result as an object and several as an array.
- **`pctl azure eam add-assignment`, `remove-assignment`, `get-request`** — grant and revoke
  access package assignments by email address, display name or object ID. Both are
  idempotent, and `--wait` polls each request until it settles and exits 5 if any did not
  reach `delivered`, bounded by `--wait-timeout`.
- **`pctl azure eam delete-package`** — delete an access package. The only destructive
  command in `pctl`, and the only one that asks before acting.
- **Aliases** — `enterprise-apps` and `service-principals` reach `sp`, `app-registrations`
  and `applications` reach `apps`, `entitlement-management` and `access-packages` reach
  `eam`, since Graph and the portal disagree on every one of these names.
- **A wiki, published from the repository.** `docs/wiki/` holds a landing page and sidebar,
  Getting Started, Finding a command, Permissions, Common options, Output and exit codes,
  Troubleshooting, one page per `pctl azure` service and one for `pctl aws ddb`.
- **Wiki publishing in CI.** Publishing a release pushes the `docs/wiki/` of the release
  tag to the GitHub wiki. A release with nothing to change pushes nothing, and a missed
  release is repaired by the next one.
- **Wiki checks on pull requests.** A pull request that changes `docs/wiki/` validates the
  pages and reports what would change in the wiki, without pushing. It fails on a missing
  `Home.md`, a subdirectory, or a link to a page that does not exist.

## Changed

- **Breaking: every command value is now behind a named flag.** There are no positional
  arguments anywhere in the CLI. Eight commands change their calling convention, seven of
  which shipped in v0.1.0, and each exits 2 until callers are updated:

  | before                           | after                 |
  | -------------------------------- | --------------------- |
  | `pctl azure groups get NAMES...` | `--name` (repeatable) |
  | `pctl azure groups members NAME` | `--group`             |
  | `pctl azure raw PATH`            | `--path`              |
  | `pctl aws ddb describe TABLE`    | `--table`             |
  | `pctl aws ddb scan TABLE`        | `--table`             |
  | `pctl aws ddb query TABLE`       | `--table`             |
  | `pctl aws ddb get TABLE KEY`     | `--table --key`       |
  | `pctl completion SHELL`          | `--shell`             |

  Positional order was the one class of mistake the CLI could not catch:
  `add-assignment "$PKG" ann@company.com` and the same two arguments reversed are both valid
  syntax and only one is right, which on a write is a bad way to find out. Multi-value
  inputs repeat the flag (`--owner a --owner b`) rather than splitting on commas, because a
  display name may legitimately contain one; `--emails` stays comma-separated, where it
  cannot.

- Graph transport collection helpers are now collection-scoped and shared across `groups`,
  `servicePrincipals`, `users` and `applications`. The group methods keep their signatures
  and behaviour, and every existing `groups` test passes unchanged.
- Directory lookups moved to `azure/common.py` when `users` became the second caller, so an
  address matched one way in one command cannot be matched differently in another.
- `.env.example` values are empty rather than all-zero GUIDs, which could be mistaken for
  something real.
- CI lint installs without building the project and runs ruff with `--no-sync`, and the push
  trigger is scoped to `main` so a branch push no longer produces a second run reporting
  `test` as skipped.

## Fixed

- Graph error messages now name the request that failed. A command may make several before
  one fails, and "Graph rejected the token" alone did not say which.
- A 403 now says it is a consent problem rather than an authentication one, and points at
  clearing the cached token, since a token issued before consent does not carry the new
  role.
- The README's Graph permission table was wrong about which permission covers which
  command.

## Notes

- **New Graph permissions**, all admin-consented. `Application.Read.All` or
  `Directory.Read.All` for `apps` and the `sp` reads. `EntitlementManagement.Read.All` for
  the `eam` reads and `EntitlementManagement.ReadWrite.All` for its writes, including
  `delete-package`. `Application.ReadWrite.All` or `Directory.ReadWrite.All` for
  `sp add-owner` and `remove-owner` only. `Synchronization.ReadWrite.All` for
  `sp provision` only. A missing permission surfaces as exit 5 with
  `Authorization_RequestDenied`.
- **A 200 from `sp provision` does not mean a subject was provisioned.** The verdict is JSON
  encoded inside the response body, and a subject that is out of scope or unassigned comes
  back as a skip with nothing provisioned. Only a `RedundantExport` skip — source and target
  already matching — counts as success. Anything unrecognised counts as failed.
- **Assignments are not written directly.** `add-assignment` and `remove-assignment` create
  a request that Graph processes afterwards, so without `--wait` exit 0 does not mean the
  access exists, or is gone. That matters more for revocation than for granting.
- **`eam delete-package` is deliberately strict.** No `--match` and no substring fallback,
  unlike every other `eam` command: an exact name or an object ID only, because `Retired`
  resolving to `Retired Access` is not a mistake worth risking. It asks before acting unless
  `--yes` is passed, declining exits non-zero, and it checks for assignments first because
  Graph refuses to delete a package that has any.
- **Entitlement management has a narrower query surface.** `$select`, `$filter` and
  `$expand` work; `$search` and `$count` do not. So there is no `--search` and no
  `--count-only` there, and `--contains` and `--match contains` filter locally after
  fetching the collection.
- `sp provision` sends one request per subject, sequentially: Graph rate limits that action
  to 5 requests every 10 seconds, far tighter than the rest of the API.
- `--principal` filters client-side, because Graph does not support `$filter` on
  `principalDisplayName` for these relations. Every page is fetched regardless, so it
  narrows what is rendered rather than what is transferred.
- `--match` and `--principal-match` are independent: the first resolves the application, the
  second filters its assignments.
- An application has two GUIDs and they are not interchangeable. `appId` is shared with its
  service principal; `id` is its own directory object. `apps get` tries a bare GUID as an
  `appId` first, then as an object ID.
- **The wiki is a mirror, not a place to edit.** The sync deletes any page that exists only
  in the wiki and overwrites any page edited there. Change `docs/wiki/` and open a pull
  request.
- **The wiki describes the latest release, not `main`.** A wiki has one live version, so
  documentation for unreleased work stays in the repository until the release that ships
  it.
- **First release only: create the wiki repository by hand.** GitHub creates it when the
  first page is saved in the Wiki tab, and has no API for it. Until then the `wiki` job
  fails with a message saying so.
- **Wiki link anchors are not validated.** The pull request check confirms that a linked
  page exists, not that a `#heading` inside it does.
- **Contributor guidance was refreshed in the same release.** The steering files now
  describe the current package tree, the three test tiers, the GitHub Actions pipeline and
  the release flow. This changes nothing for users of the CLI.
- Requires Python 3.14 or newer, unchanged from v0.1.0.
