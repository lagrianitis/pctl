# Overview

Show what credentials an app registration holds and when they expire. A client secret that
lapses breaks the application that uses it, usually at a bad moment and with an error that
names the symptom rather than the secret. Today the answer lives in the portal, one app at a
time, or in a hand-written Graph request.

This milestone adds `pctl azure apps get-client-secrets`: given an app registration by app ID
or display name, it lists its client secrets and certificates with their dates, how
many days each has left, and whether it has lapsed. It can also be told to fail when one is
close, so a pipeline can catch an expiring secret before an outage does.

Listing shows metadata only. Graph never returns the value of an existing secret, only a
name, a key ID, a short hint and the dates, and this milestone does not try to get around
that. The value of a new secret is returned once, at creation, which is why the milestone
also adds the two writes that go with listing:

- `pctl azure apps add-client-secret` creates a client secret and keeps its value. The value
  is shown once, so the command refuses to run unless it has somewhere to go: an AWS
  Secrets Manager secret named with `--store-in`, which receives `<app>_<name>_client_id`,
  `_client_secret` and `_client_exp_date`, or `--show-secret`. The destination is checked
  before the secret is created, and a secret that could not be stored is removed again.
- `pctl azure apps remove-client-secret` removes one, by key ID only. A secret with more than
  30 days left, or no end date, needs `--force`.

For the Engineering Portfolio this is the kind of extension the structure was built for. The
commands are actions added to an existing service, sharing one way of naming the app
(`--app-name` or `--app-id`), and the transport gains only `addPassword` and
`removePassword`. The parts that are new are the rule that turns a date into a status, kept
free of the clock so it can be tested exactly at its boundaries, and the care taken over a
value that can be lost: nothing is created without a destination, and a create is never
repeated after an unknown outcome.

Documentation as Code continues: the commands, their columns, the expiry window, the
Secrets Manager key format, the IAM and Graph permissions and the exit code are documented in
the README and on the wiki, published with the release.

# Objectives

- Show every secret and certificate on an app registration without opening the portal.
- Find the app the way `apps get` does, so the same name or GUID works in both commands, and
  refuse an ambiguous display name rather than choosing one.
- Say how long each credential has left and whether it has already lapsed, in terms that do
  not depend on reading dates.
- Make an expiry check scriptable on the exit code alone, so a pipeline can fail ahead of an
  outage.
- Never print or log a secret value or certificate key material, and never go beyond what
  Graph returns.
- Test the date rule at its boundaries without depending on today's date.
- Create a client secret without ever losing its value: refuse to create one with nowhere to
  put it, vet the destination first, and undo the creation if storing fails.
- Never repeat a create after an outcome that is unknown, since that could leave two live
  secrets and only one of them held.
- Make removal deliberate: by key ID only, and with `--force` when the secret may still be
  in use.

# Deliverables

## Repository

- `src/pctl/azure/applications/get_client_secrets.py`: the `get-client-secrets` action, and its entry in
  the `apps` `LAZY_SUBCOMMANDS`.
- The credential rows: type (secret or certificate), name, key ID, start and end date, days
  remaining and status, plus the hint for a secret.
- `--expiring-within DAYS` for the window that counts as expiring, and `--fail-on-expiry`,
  which lists everything and then exits 6 when a credential has expired or is expiring.
- `CheckFailedError` and exit code 6 in `errors.py`, for a check that ran and said no.
- A clock read in one place, `utcnow()`, which the end-to-end tests pin.
- `src/pctl/azure/applications/add_client_secret.py` and `remove_client_secret.py`: the
  `add-client-secret` and `remove-client-secret` actions, with their `LAZY_SUBCOMMANDS`
  entries.
- `--app-name` and `--app-id` on all three commands, from one shared decorator, with
  `resolve_app` in `common.py` so `--app-id` does no display name search.
- `GraphClient.add_application_password` and `remove_application_password`, and an
  `idempotent=False` mode on `request` that retries only 429, so a create is never repeated
  after a server error or a dropped connection.
- `SecretObject` in `secrets.py`: checks that a Secrets Manager secret exists, is live, is a
  JSON object and has room for the keys, then adds keys without disturbing the others.
- The `<app>_<name>_client_id`, `_client_secret` and `_client_exp_date` key format, with
  names lowercased and anything but letters and digits turned into an underscore.
- The force rule for removal, `requires_force`, sharing the window `credential_status` uses.
- The `["azure", "apps", "get-client-secrets"]`, `add-client-secret` and
  `remove-client-secret` paths in `COMMAND_PATHS` in the smoke tier.
- Coverage across all three tiers: unit for the status rule, the force rule and their
  boundaries, smoke for the help surface and argument errors, e2e for the real command paths
  against a faked Graph and a Secrets Manager faked by moto.

# Success Criteria

- `pctl azure apps get-client-secrets --app-name "<name>"` lists one row per secret and per certificate
  with its type, display name, key ID, start and end date.
- `--app-id` finds the app by its `appId` with no display name search, and `--app-name`
  honours `--match`. Giving both or neither exits 2, an ambiguous name exits 2, and a name or
  `appId` that matches nothing exits 4.
- A credential whose end date has passed is `expired`, one ending within the window is
  `expiring`, and any other is `valid`. The boundaries are tested exactly: at the window,
  one second inside it, and already past.
- With `--fail-on-expiry`, the command exits 6 when any credential is expired or expiring and
  0 when all are valid, and 6 is in the exit-code tables.
- An app with no credentials exits 0 and says so on stderr.
- No secret value or key material appears in any output format.
- The table and `-o json` carry the same fields, and a run under a fixed clock is
  deterministic.
- `pctl --help` imports none of boto3, botocore, httpx, uvloop or h2, with the new path added
  to `LAZY_PATHS`.
- `uv run ruff check .` and `ruff format --check .` clean, and `uv run pytest -n auto` green
  with **zero warnings**, needing no tenant, no AWS account and no network.
- The permission the command needs is stated and checked against what `apps get` needs.
- `add-client-secret` with neither `--store-in` nor `--show-secret` exits 2 and sends nothing.
  With `--store-in`, a missing, non-JSON, scheduled-for-deletion or clashing destination exits
  2 before the secret is created, and `--overwrite` replaces only the keys it names.
- The new value is stored under the three keys with every other key kept, and appears in no
  output, log or error unless `--show-secret` asked for it, then once.
- A failed write removes the new secret and exits 5. A name the app already uses is refused.
- A 500 or dropped connection on the create is not retried, and a 429 is.
- `--valid-for-days` accepts 1 to 365 and exits 2 outside that.
- `remove-client-secret` removes an expired secret, or one ending within 30 days (the 30th
  included), without `--force`. It refuses one with more time left, or no end date, until
  `--force` is given, and sends nothing when it refuses.
- `remove-client-secret` accepts a key ID only, refuses a certificate, and exits 4 for a key
  ID the app does not have.
