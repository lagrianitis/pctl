# Overview

Extend the `azure` case from one service to five, and from reading the directory to
changing it. v0.1.0 could list groups; v0.2.0 answers the questions that actually come up
in access reviews — who is assigned to this application, who owns it, what access packages
exist and who holds them — and then lets you do something about the answer.

The question that started it was an access check: "is this group assigned to this SCIM
application?", which previously meant a hand-written Graph request and reading GUIDs out of
raw JSON. Answering it well turned out to require users, application registrations and
entitlement management too, because the objects are joined and a half-answer sends you back
to the portal.

For the Engineering Portfolio this milestone is the first real test of whether the shape
v0.1.0 established holds under load. Adding a service should mean adding a package and one
entry in a table, not reshaping the case around it. Four new services later, `groups`
behaves exactly as it did, which is the evidence.

It is also the first milestone with a **breaking change** and the first that writes
anything, so it is where the project's conventions about safety get written down rather
than assumed: named arguments over positional ones, idempotent writes, confirmation before
destruction, and never reporting success for something that did not happen.

Documentation as Code continues: usage, permissions, and the behaviours worth knowing
before relying on them all land in the repository alongside the code, through the same
reviewed pull requests.

---

# Objectives

- Extend the `case → service → action` shape to four new services without changing how
  `groups` behaves, proving the structure extends rather than bends.
- Answer the access-control questions directly — assignments, owners, access packages and
  their holders — so none of them needs a hand-written Graph request.
- Make every write safe to re-run from a pipeline: read current state first, report a
  no-op as information, and never require a dry run to be confident.
- Never report success for a change that did not take effect, even when the provider
  returns HTTP 200.
- Remove positional arguments from the CLI, so argument order can no longer silently
  change what a command acts on.
- Keep `pctl --help` free of provider SDKs as the surface grows, so the tool stays fast to
  invoke.

# Deliverables

## Repository

- `src/pctl/azure/service_principals/`: the `sp` group with `list`, `get`, `assignments`,
  `owners`, `add-owner`, `remove-owner` and `provision`.
- `src/pctl/azure/users/`: the `users` group with `get`, resolving a person from an email
  address, display name or object ID.
- `src/pctl/azure/applications/`: the `apps` group with `list` and `get`, including the
  `appId` join from a registration to its service principal.
- `src/pctl/azure/entitlements/`: the `eam` group with `list-packages`, `get-package`,
  `delete-package`, `list-catalogs`, `get-catalog`, `list-assignments`, `add-assignment`,
  `remove-assignment` and `get-request`.
- `src/pctl/azure/common.py`: the directory lookups more than one service needs, lifted out
  of `service_principals/common.py` when `users` became the second caller.
- Graph transport extended with service principal, user, application, entitlement
  management and synchronization paths, and a separate query builder for entitlement
  management, whose collections reject `$search` and `$count`.
- Every command value behind a named flag, with a tree-walking test that fails if any
  command reintroduces a positional argument.
- Coverage across all three tiers — unit for pure functions, smoke for the CLI surface,
  e2e for the real command path with only the provider boundary faked.

# Success Criteria

- `pctl azure sp assignments --app "<app>" --principal "<group>"` exits 0 when assigned and
  4 when not, so an access check is scriptable on the exit code alone.
- `appRoleId` never reaches the user as a bare GUID unless `--no-role-names` was asked for;
  the all-zero GUID renders as Default Access.
- Every write is idempotent: adding an existing owner, removing an absent one, or assigning
  someone who already has access exits 0 and reports the no-op rather than erroring.
- `sp provision` and the `eam` assignment writes exit non-zero when the change did not
  apply, including when the provider answered 200 with a failure verdict in the body, and
  classify anything unrecognised as not-applied rather than as success.
- `eam delete-package` refuses a substring name match, requires confirmation unless `--yes`
  is passed, and exits non-zero when the confirmation is declined.
- No command in the tree declares a positional argument, asserted by a test rather than by
  review.
- `uv run --no-sync ruff check src/` and `ruff format --check src/` both clean.
- `uv run pytest -n auto` green with **zero warnings**, needing no tenant, no AWS account
  and no network.
- `pctl --help` imports none of boto3, botocore, httpx, uvloop or h2, with the new command
  paths added to `LAZY_PATHS`.
- Every `groups`, `token` and `raw` test from v0.1.0 still passes, apart from the calling
  convention changes recorded as breaking.
